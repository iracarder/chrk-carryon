# Поместится ли в ручную кладь?

Одностраничный инструмент: вводишь габариты и вес сумки — получаешь вердикт по 30 авиакомпаниям
и наглядное сравнение с рамкой-сайзером. Страница `index.html` самодостаточна: ни CDN, ни внешних
запросов, ни аналитики. Открывается двойным щелчком, работает офлайн и с телефона.

Два языка, переключатель в шапке: RU и EN. Язык сохраняется в браузере и переносится ссылкой
(`#l=en`).

## Живые адреса

- https://chrk-carryon.netlify.app — основной, на Netlify.
- GitHub Pages — см. раздел ниже.

## Принципы, которые стоит не ломать

**Стороны сравниваются по убыванию.** Сумку разрешено поворачивать, поэтому `[длина, ширина, высота]`
сортируются перед сравнением с лимитом. Без этого сумка 55×40×23 не проходит там, где прошла бы 55×23×40.

**«Впритык» — это предупреждение, а не отказ.** Запас ≤ 1 см по стороне или ≤ 0,5 кг по весу даёт
жёлтый статус: мягкая набитая сумка на трапе может не пройти жёсткую рамку. Красный статус — только
реальное превышение, и то с учётом допуска `Запас на сайзер`.

**Линейный размер — отдельная проверка, а не следствие габаритов.** Некоторые перевозчики (KLM,
IndiGo, AZAL, EgyptAir) ограничивают сумму трёх сторон, а не каждую сторону по отдельности. Проверка
габаритов не покрывает такой лимит, поэтому `linear` проверяется сам по себе.

**Вес не переводится в дюймы.** Дюймы — только для длин. Пересчёт веса при переключении единиц был бы
молчаливой порчей данных.

**Кириллица в английском режиме — это баг.** Интерфейс, примечания и названия авиакомпаний лежат в
словаре `I18N` и в полях `*En` данных; обращаться к ним можно только через `t()`, `nameOf()`, `noteOf()`,
`srcOf()`, `optLabel()`, `presetLabel()`. Обход этих хелперов — прямой путь к русскому тексту внутри
английской страницы. Отлавливает `test-i18n.js`.

**Внешних запросов быть не должно.** Инвариант проверяет не «нет ссылок», а «ничего не грузится»:
запрещены внешние `<script src>`, `<link href>`, `<img src>`, `<iframe>`, `fetch`, `XMLHttpRequest`,
`sendBeacon`, динамический `import()` и `@import`. Исходящие `<a href>` разрешены — переход по клику
запросом не является, — но обязан нести `noopener`, а в партнёрском блоке ещё и `sponsored`.

**Вердикт не ищется по тексту причины.** Тип вердикта выводится из состояния расчёта, а не из
сравнения подстрок: любая правка формулировки или переключение языка иначе ломают результат.

## Тесты

```
node test-logic.js    # данные, правила, сортировки, сводка, ссылка, автономность
node test-i18n.js     # словарь, разметка, переводы данных, переключение языка
node .smoke.js        # весь рендер поверх минимального DOM-шима
```

Логика и рендер разнесены маркером `/* ---------------- рендер ---------------- */`: `test-logic.js`
поднимает в `vm` только то, что до него, поэтому проверки правил не зависят от DOM.

## Как править данные правил

Массив `AIRLINES`. У каждой авиакомпании есть `opts` — варианты по тарифам, потому что у лоукостеров
лимиты различаются между тарифами сильнее, чем между авиакомпаниями.

Правя правило, меняй оба языка: `label` + `labelEn`, `note` + `noteEn`. Для «Аэрофлота» и
«Уральских авиалиний» ещё `nameEn`, для русской подписи источника — `srcEn`. Проверка
`test-i18n.js` специально требует английские варианты везде, где в русском есть кириллица.

`DATA_CHECKED` внизу массива — месяц проверки. Он показывается в интерфейсе и попадает в сводку:
пользователь должен видеть, насколько свежие перед ним цифры.

## Ограничения данных

Прямо в интерфейсе и в примечаниях, не прячем:

- **Aeroflot** — по внешним пересказам, официальных норм на сайте нет (сайт отдаёт 503).
- **EgyptAir** — противоречие между страницами сайта: 7 кг / 115 см против 8 кг / 118 см.
- **Tajik Air** — норм не публикует вовсе, всё в билете.
- **Georgian Airways** — габариты не публикует, только линейный размер.
- **Asky Airlines** — только вес.

Это не baggage approval. Перед вылетом сверяйся с сайтом перевозчика и со своим билетом.

## Партнёрские ссылки

Блок «чемодан подходящего размера» появляется, только когда сумка реально не проходит хотя бы у
одной выбранной авиакомпании. Это момент максимального намерения купить: человек уже знает, что сумка
велика. Ссылки — обычные поисковые запросы магазинов с подставленным размером.

Что здесь важно: блок **не ломает обещание автономности**. Это обычные `<a href>`, запроса не
происходит, пока человек сам не кликнул. Поэтому аналитика не нужна и не используется — измеряется
только переход. Каждая ссылка помечена `rel="sponsored noopener"`, и под блоком стоит явное
раскрытие, что это партнёрские ссылки и цена от этого не меняется.

Как сделать ссылки партнёрскими: добавь в `base` параметры выплат своей партнёрской сети.

```js
{ key:"ozon", ru:"Ozon", en:"Ozon", langs:["ru"], q:"чемодан",
  base:"https://www.ozon.ru/search/?text=" },   // → "...?text=...&oza_partner_id=XXX"
```

Подходящие программы: Travelpayouts/Aviasales (за переходы и бронирования), Ozon и Яндекс.Маркет
(партнёрские кабинеты), Amazon Associates, eBay. Условия и ставки везде разные — проверяй перед
подключением.

Ссылки в `SHOPS` проверены только частично. Amazon открывается и отдаёт выдачу; Ozon, Яндекс.Маркет,
Wildberries и eBay отвечают 403/498 на автоматические запросы — это их анти-бот, а не битая ссылка,
но и подтвердить работоспособность без живого клика нельзя. **Пройди по каждой ссылке в обычном
браузере один раз**, прежде чем считать блок готовым, и выброси из `SHOPS` то, что не открывается.
Битый магазин в блоке хуже, чем отсутствие блока.

Рекомендованный размер считается **тем же кодом**, что и основная проверка: перебираются пять типовых
габаритов и выбирается самый мелкий, проходящий максимум выбранных норм. В отличие от проверки
сумки пассажира, здесь совпадение с нормой засчитывается как проход: чемодан, купленный точно под
предел, — это нормальная покупка, а не риск.

## Публикация

**GitHub Pages:** Settings → Pages → Source: Deploy from a branch, ветка `main`, корень. Файл `index.html`
лежит в корне, отдельная сборка не нужна.

**Netlify:** каталог `dist/` содержит копию `index.html` — ровно то, что нужно для выкладки без
сборки. Надёжный путь — официальный CLI, он сам создаёт деплой, грузит файлы и ждёт готовности:

```
$env:NETLIFY_AUTH_TOKEN = "…"
npx --yes netlify-cli@latest deploy --dir=dist --prod --site=<site_id>
```

Ручной API работает не всегда: `POST /sites/{id}/deploys` может вернуть `state=new`, а
`PUT /deploys/{id}/files/index.html` в этом состоянии отклоняется с 401. Такой деплой повисает
навсегда, удалить его нельзя — DELETE на деплой отвечает 405. Схема работает через раз, и,
похоже, зависшие деплои блокируют очередь выкладки сайта. Если столкнулся — не набивай новые,
зови CLI.

Водяной знак `CHRK-Bishkek` — не украшение, а подпись: по странице видно, что инструмент
самодостаточный и никуда не отправляет данные.
